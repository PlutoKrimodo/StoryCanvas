## T-1 Guest-first：游客优先 / 先体验后注册

### 1. 动机

让成品显得更「商业化」：**未注册/未登录的用户也能直接体验生成**（少量图片或较少页数），
首页进来就是绘本生成功能，而不是先被拦在注册/登录页。

产品视角上，这是把「注册」从**入口门槛**前移成**转化动作**，形成
「游客体验 → 注册 → 创作 → 保存」的漏斗。

### 2. 现状与硬约束（2026-09-28 记录）

| 约束 | 位置 | 现状 | 影响 |
|------|------|------|------|
| 路由守卫 | `frontend/src/App.tsx` | `/` 包在 `ProtectedRoute` 内，未登录跳 `/login` | 需改为 `/` 公开、生成器上首屏 |
| 接口契约 | `docs/04` §8、`backend/controllers/BookController.h` | 生成 / 绘本接口均挂 `JwtFilter`，无 Token 返回 401 | 「匿名生成」属于新增契约 |
| 数据模型 | `sql/init.sql` | `books.user_id`、`generation_tasks.user_id`、`generated_images.user_id` 均为 `NOT NULL` 外键 | 匿名没有 `user_id`，结果**无法落库** |
| 已预留 | `docs/16` §7.4 | 限流已设「**匿名** 100 次/分、认证 1000 次/分、AI 生成 10 次/分」 | 说明设计上本就允许匿名请求，只是未用到生成上 |
| 生成前端 | `frontend/src/pages/generation/Generate.tsx` + `components/ai/` | ✅ Phase 5 已实现 | 「首页即生成器」只差把它搬上首页 |

**结论**：观感便宜、能力昂贵。两者要拆开评估。

### 3. 目标拆解：观感层 vs 能力层

#### 观感层（低成本，预计 1–2 天）

- 首页 `/` 公开，首屏即生成器（或"立即体验"区）
- 生成动作触发**轻量登录 Modal**，而不是整页跳转 `/login`
- 额度文案：「游客可试 1 张，登录后可生成 10 张」
- 结果页提供「登录后可保存 / 生成更多」的引导

> 这一层**不改数据模型、不改接口契约**，纯前端 + 路由调整。

#### 能力层（高成本，需单独评估）

- 真正允许匿名出图并落库
- 匿名额度控制（计数 + 限制 + 429）
- 匿名结果的归属与「注册后认领」

### 4. 计划时机与理由

```
Phase 4 (AI 基础) → Phase 5 (生成闭环·核心) → Phase 6 (预览/历史) → ★ T-1 → Phase 10 (测试)
```

- ❌ **不早于 Phase 5**：生成闭环还不存在，没有「可匿名的东西」；且 Phase 5 是核心交付，
  不宜中途插入 auth / 数据模型改动。
- ✅ **Phase 5 之后，建议 Phase 6 之后**：匿名结果需要一个「落点」，
  而 Phase 6 的「生成预览与历史」正好承担这个角色。
- ❌ **不晚于 Phase 10**：测试 / 部署 / 报告是硬交付，不能被挤占。

### 5. 动手前必须先定的小决策（**Phase 5 开工前**就要定）

这两点几乎零成本，但决定了后续要不要返工；**即使最终不做 T-1 也不亏**（本来就更干净）：

1. **生成器做成「可复用组件」，不要写死在 `/generate` 页面里**
   → 以后把它搬上首页（`/`）只是挪位置，而不是重写页面 + 重排路由守卫。
   - 相关位置：`frontend/src/pages/generation/`、`frontend/src/components/ai/`
   - ✅ **已落地（2026-09-30）**：生成器为独立组件 `components/ai/GenerationForm.tsx`，
     `pages/generation/Generate.tsx` 只是它的一个宿主页面。
2. **「生成一张图」与「保存到某个绘本」解耦**
   → 让生成动作不天然依赖 `book_id`，匿名「先出图、登录后再存入绘本」才顺理成章。
   - 相关位置：Phase 5 的 `GenerationService` / `GenerationTask` 数据流
   - ✅ **已落地（2026-09-30）**：`CreateGenerationRequest.book_id` 可选；
     AI 侧未绑定绘本时按 `unassigned` 目录落盘；前端「保存到绘本」弹窗事后绑定 `image_id`。

### 6. 待决策清单

| # | 问题 | 候选方案 | 影响 |
|---|------|---------|------|
| 1 | 匿名身份如何识别 | Cookie / 设备指纹 / IP / 匿名 token | 决定额度能否被轻易绕过 |
| 2 | 匿名额度记在哪 | 内存 / Redis / 数据库 | 进程重启是否清零；是否需要引入 Redis |
| 3 | 匿名结果归属 | 影子用户 / `user_id` 允许为空 / 仅临时存储 | 直接决定数据模型改动量 |
| 4 | 注册后能否「认领」 | 是 / 否 | 决定转化体验的完整度 |
| 5 | 防刷强度 | 与 Provider（Mock / 真实）挂钩 | 接真实图像 API 后必须收紧 |

- **前端**：`App.tsx`（路由与守卫）、`pages/home/Home.tsx`、`pages/generation/`、
  `components/ai/`、`stores/authStore.ts`、`api/client.ts`（401 拦截与刷新逻辑）

- **数据**：`sql/init.sql`（`user_id` 是否可空 / 新增 guest 表 / 额度表）
- **契约与安全**：`docs/04`（匿名生成接口）、`docs/10`（限流策略落地）
- **文档**：`docs/13`（演示流程需重排）、`docs/16` §8.x（阶段排期）

### 8. 对演示与报告的影响

- **演示顺序会变**：由「注册 → 登录 → 创建绘本 → 生成」变为
  「**直接生成 → 触发登录 → 保存**」（见 `docs/16` §13.3 的 5 分钟流程，需重排）。
- **报告素材**：可讲「把注册从入口前移到转化点」的产品设计，
  答辩时通常比多写一个 CRUD 更有说服力。

### 9. 范围与风险

- 属于**范围追加**：核心 MVP（用户系统 + 智能图像生成）不依赖它。
- 时间不足时的**兜底**：只做「观感层」，不动数据模型、不改接口契约。
- 若接入真实图像生成 API，**匿名额度必须先收紧**，否则是成本敞口。

### 10. 验收标准（若实施）

- 未登录可访问首页 `http://localhost:5173/` 并看到生成器
- 未登录可生成 N 张（默认 1），额度用尽后有明确提示
- 登录后可将匿名结果保存到自己的绘本
- 超额度返回 **429**，与 `docs/16` §7.4 的匿名限流口径一致
