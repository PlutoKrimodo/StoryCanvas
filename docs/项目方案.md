## 2. 项目概述

### 2.1 建设目标

构建一个"输入故事文字 → AI 生成插画 → 在线排版编辑 → 导出绘本"的完整系统，作为课程设计项目，需同时满足以下验收要求：

1. 功能完整：覆盖 MVP 全部功能点
2. 架构清晰：前后端分层、职责单一、接口规范
3. 可演示：端到端流程可在数分钟内完成
4. 可报告：具备完整的报告素材与图表

### 2.2 目标用户

| 用户类型 | 使用诉求 |
|---------|---------|
| 家长 | 为孩子快速制作个性化绘本 |
| 幼儿教师 | 制作教学用图画故事 |
| 绘本创作者 | 快速产出草稿与配图 |

### 2.3 使用场景

用户用一段自然语言描述故事，系统解析出角色、场景与动作，生成风格化插画，用户在画布中排版多页内容，最终导出为 PDF 绘本。

### 2.4 系统边界

- **系统内**：用户体系、绘本项目管理、AI 文本解析与图像生成、Canvas 在线编辑、页面管理、PDF 导出。
- **系统外（依赖）**：LLM 服务、图像生成服务（MVP 阶段以 Mock Provider 替代）。

## 3. 需求范围

### 3.1 功能需求

| 模块 | 功能点 | 优先级 |

| 元素 | 元素增删改（MVP 仅图片元素） | MVP |

| 编辑器 | 添加图片、移动、缩放、保存与还原 | MVP |
| 导出 | 导出 PDF | MVP |

### 3.2 非功能需求

| 维度 | 要求 |
|------|------|
| 性能 | API 平均响应 < 500ms；AI 生成 < 60s；前端首屏 < 3s |
| 并发 | 支持 100+ 并发请求（测试目标） |
| 安全 | bcrypt 密码哈希、JWT 鉴权、资源归属隔离、参数化查询、输入校验、文件类型与大小校验、接口限流 |

| 可扩展 | AI Provider 抽象（可更换服务商）、存储抽象（本地 → 对象存储） |

### 3.3 MVP 边界

**必须实现**

- 用户注册/登录、JWT 认证
- 创建绘本、查看绘本列表
- AI 文本解析、AI 图像生成
- 图片预览、添加图片到页面
- 移动/缩放图片
- 页面管理
- 导出 PDF

**明确不做（延后或放弃）**

- 角色一致性与角色管理
- 旋转、文字编辑、撤销/重做、图片裁剪
- 生成历史、多格式导出、图片上传增强
- Redis 队列、并发测试、性能测试

**加分项**

- 更完善的 UI 设计、更多艺术风格、生成历史记录、撤销/重做

## 4. 技术选型

### 4.1 选型总表

| 层级 | 技术 | 版本 | 选型理由 |
|------|------|------|---------|
| 前端框架 | React + TypeScript | 18.x / 5.x | 生态成熟、类型安全 |
| 构建 | Vite | 5.x | 启动与构建快 |
| UI | Ant Design + Tailwind CSS | 5.x / 3.x | 组件齐全，快速成型 |
| 画布 | Fabric.js | 需锁定版本 | Canvas 编辑事实标准 |
| 状态管理 | Zustand | 4.x | 轻量、学习成本低 |
| 路由/请求 | React Router / Axios | 6.x / - | 标配 |
| 后端语言 | C++ | C++17 | 课程技术要求 |
| 后端框架 | Drogon | 1.x | 高性能、功能完整 |
| 构建工具 | CMake | 3.16+ | 标配 |
| 后端库 | nlohmann/json、jwt-cpp、spdlog、drogon-orm | - | JSON/JWT/日志/ORM |
| AI 服务 | Python + FastAPI | 3.10+ / 0.104+ | 异步、类型校验、自动文档 |
| AI 抽象 | Provider 模式（LLM / Image） | - | 可切换、可 Mock |
| 数据库 | PostgreSQL | 15 | JSONB 存画布数据、UUID 主键 |
| 缓存 | Redis | 7.x（可选） | MVP 可用内存队列替代 |
| 部署 | Docker + Docker Compose + Nginx | - | 一键交付 |

### 4.2 关键技术决策

1. **后端框架选型**：在 Drogon / Crow / Oat++ 中选 Drogon（功能完整、性能强），接受其学习成本。
2. **状态管理选型**：在 Zustand / Redux / Jotai 中选 Zustand（轻量、简单）。
3. **AI 任务状态归属**：任务状态由 C++ 后端持有并落库，AI Service 保持无状态，前端只对接后端一个状态源。
4. **异步机制**：MVP 使用内存队列 + 工作线程，Redis 队列作为第二阶段升级项。
5. **画布数据唯一来源**：以 `book_pages.canvas_data`（Fabric 全量 JSON）为准。
6. **存储抽象**：定义统一存储接口，MVP 用本地文件系统实现，预留对象存储实现。
7. **AI Provider 抽象**：LLM 与 Image 各自定义基类，Mock 实现用于开发与测试，真实实现作为开关。

## 5. 系统架构

### 5.1 架构总览

```
┌─────────────────────────────────────────────┐
│              前端 (React + TS)               │
│    用户界面 / 绘本编辑器 / AI 生成界面        │
└─────────────────────────────────────────────┘
                     │ HTTP/REST + JWT
                     ▼
┌─────────────────────────────────────────────┐
│             C++ 后端 (Drogon)                │
│  用户 / 绘本 / 页面 / 生成任务 / 导出 / 文件  │
└─────────────────────────────────────────────┘
                     │ HTTP/REST（内网 + API Key）
                     ▼
┌─────────────────────────────────────────────┐
│          Python AI Service (FastAPI)         │
│  文本解析 / Prompt 优化 / 图像生成 / Provider │
└─────────────────────────────────────────────┘
                     │ HTTP/REST
                     ▼
┌─────────────────────────────────────────────┐
│        外部 AI 服务（LLM / 图像生成）         │
└─────────────────────────────────────────────┘

┌─────────────────────────────────────────────┐
│  数据层：PostgreSQL / Redis / 本地文件存储    │
└─────────────────────────────────────────────┘
```

### 5.2 各层职责

| 层 | 职责 | 约束 |
|----|------|------|
| 前端 | 界面渲染、路由守卫、状态管理、Canvas 交互、任务轮询 | 不承载业务规则 |
| C++ 后端 | 认证鉴权、业务逻辑、数据持久化、任务编排、文件管理、导出 | 唯一对外 API 出口 |
| AI Service | 文本解析、Prompt 优化、图像生成、Provider 抽象 | 无状态，仅内网调用，需内部 API Key |
| 数据层 | 结构化数据、缓存、文件 | 文件按用户/绘本分层存储 |

### 5.3 后端分层

| 层 | 职责 |
|----|------|
| Controller | 路由、参数解析、调用 Service、构造响应 |
| Service | 业务逻辑、事务、编排外部服务 |
| Repository | 数据访问、SQL、数据映射 |
| Model / DTO | 数据实体与传输对象、序列化与校验 |
| Filter | JWT 校验、CORS、限流 |
| Utils | JWT、密码、文件、校验、配置 |

**分层红线**：Controller 不写业务逻辑；Repository 不写业务规则；避免循环依赖。

### 5.4 通信设计

| 链路 | 协议 | 认证 | 超时 |
|------|------|------|------|
| 前端 → C++ 后端 | HTTP/JSON，URL 版本 `/api/v1` | JWT Bearer | 30s |
| C++ 后端 → AI Service | HTTP/JSON（内网） | 内部 API Key | 60s（可配） |
| AI Service → 外部 AI | HTTP/JSON | 服务商 API Key | LLM 30s / 图像 120s |

### 5.5 部署形态

| 环境 | 形态 |
|------|------|
| 开发 | Vite Dev Server(5173) + Drogon(8080) + Uvicorn(8000) + PostgreSQL(5432) + Redis(6379) |
| 生产 | Docker Compose 编排 + Nginx 反向代理 + 数据卷持久化 |

## 6. 数据设计

### 6.1 数据表清单

| 表 | 用途 | 关键字段 |
|----|------|---------|
| users | 用户 | id(UUID)、username、email、password_hash、avatar、is_active、created_at、updated_at |
| books | 绘本 | id、user_id、title、description、cover_image、status、created_at、updated_at |
| book_pages | 页面 | id、book_id、page_number、title、canvas_data(JSONB)、thumbnail、created_at、updated_at |
| page_elements | 元素明细 | id、page_id、element_type、position_x/y、width/height、rotation、style_data、content、z_index、is_visible |
| characters | 角色 | id、user_id、name、description、age、appearance、style_info |
| generation_tasks | 生成任务 | id、user_id、book_id、page_id、prompt、original_text、parsed_data、status、result_url、error_message、model_used、parameters、completed_at |
| generated_images | AI 生成图 | id、task_id、user_id、file_path、file_size、width/height、format、prompt_used、is_favorite |
| files | 用户上传文件 | id、user_id、original_name、storage_path、file_size、mime_type、file_hash、expires_at、metadata |

### 6.2 实体关系

```
users ──1:N──▶ books ──1:N──▶ book_pages ──1:N──▶ page_elements
  │
  ├──1:N──▶ characters
  │
  ├──1:N──▶ generation_tasks ──1:N──▶ generated_images
  │
  └──1:N──▶ files
```

### 6.3 删除与清理策略

- 删除用户级联删除其绘本、角色、生成任务、上传文件
- 删除绘本级联删除其页面
- 删除页面级联删除其元素
- 删除生成任务级联删除其生成图片
- 删除数据库记录时同步清理物理文件；定期清理临时文件与孤立文件
- 重要数据可引入软删除字段（可选）

### 6.4 状态设计

| 对象 | 状态 | 说明 |
|------|------|------|
| 绘本 | draft / published / archived | 草稿 / 已发布 / 已归档 |
| 生成任务 | pending / processing / completed / failed / cancelled | 待处理 / 处理中 / 完成 / 失败 / 已取消 |

### 6.5 时间与索引规范

- 所有表统一 `created_at` / `updated_at`，使用带时区时间戳，存储 UTC
- 外键字段全部建索引
- 高频查询建索引：用户邮箱与用户名、绘本归属、页面归属、任务归属与状态
- 唯一约束：用户名唯一、邮箱唯一、同一绘本内页码唯一

### 6.6 待修正的数据问题

| 序号 | 问题 | 建议 |
|------|------|------|
| 1 | `generated_images.task_id` 非空，但用户上传图无任务来源 | 新增 `files` 表区分上传文件与生成图片 |
| 2 | `page_elements` 与 `canvas_data` 双写易不一致 | MVP 只以 `canvas_data` 为准，元素明细表暂不写入 |
| 3 | JSONB 字段结构缺少统一约定 | 明确 canvas_data、style_data、style_info、parsed_data 的结构 |

## 7. 接口契约

### 7.1 通用规范

- Base URL：`/api/v1`
- 认证：`Authorization: Bearer <token>`
- 内容类型：`application/json`（上传接口为 `multipart/form-data`）
- 统一响应：`{ code, message, data }`
- 错误响应：`{ code, message, errors? }`，且 `data` 必须补齐为 `null`

### 7.2 HTTP 状态码

| 状态码 | 说明 |
|--------|------|
| 200 / 201 / 204 | 成功 / 创建成功 / 删除成功 |
| 400 / 401 / 403 | 参数错误 / 未认证 / 无权限 |
| 404 / 409 / 422 | 不存在 / 冲突 / 校验失败 |
| 429 / 500 / 504 | 限流 / 服务错误 / 上游超时 |

### 7.3 模块与接口清单

| 模块 | 前缀 | 主要接口 |
|------|------|---------|
| 认证 | /auth | register、login、refresh、logout |
| 用户 | /users | me（GET/PUT）、me/password（PUT）、me/books（GET） |
| 绘本 | /books | 创建、详情、更新、删除、导出、页面子资源 |
| 页面 | /pages | 详情、更新、删除；/books/{id}/pages 创建与 reorder |
| 元素 | /elements | 新增、更新、删除、批量更新 |
| 角色 | /characters | 新增、列表、详情、更新、删除 |
| 生成 | /generation | 创建任务、查询状态、历史、取消、重新生成 |
| 图片 | /images | upload、详情、删除、列表 |
| 导出 | /books/{id}/export、/export/{task_id} | 导出、查询导出状态 |
| 健康 | /health | 数据库 / 缓存 / AI 服务状态 |

### 7.4 安全要求

| 项 | 要求 |
|----|------|
| 认证 | 受保护接口必须携带 JWT |
| 授权 | 用户只能访问自己的资源，服务端自动校验归属 |
| 限流 | 匿名 100 次/分、认证 1000 次/分、AI 生成 10 次/分 |
| 体积 | 普通请求 1MB、文件上传 10MB |
| 校验 | 入参类型、长度、格式统一校验，返回 422 与字段级错误 |

### 7.5 待统一的接口问题

| 序号 | 问题 | 建议 |
|------|------|------|
| 1 | AI Service 对外接口与后端对外接口命名易混淆 | AI 侧拆为 `analysis/parse` 与 `images/generate` 两个明确端点 |
| 2 | 过滤器返回的错误响应缺少 `data` 字段 | 统一补齐 `data: null` |
| 3 | CORS 以 Controller 实现不符合语义 | 改为过滤器或全局中间件实现 |

## 8. 模块拆解与开发顺序

固定推进顺序如下，**不跳步、不并行**：

```
环境与骨架 → 用户系统 → 绘本管理 → AI 服务基础
     → AI 生成闭环 → 在线编辑器 → 多页与导出
     → 测试完善 → 容器化部署 → 报告与演示
```

### 8.1 M0 环境与骨架（Phase 0-1，3-4 天）

| 项 | 内容 |
|----|------|
| 目标 | 本机可编译/启动三端，数据库可连通 |
| 任务 | 安装工具链与大依赖；建立仓库骨架（backend / ai-service / frontend / sql / storage / nginx / tests 与基础配置文件）；建立全部数据表；三端实现 health 接口 |
| 产出物 | 可运行的三端空壳、数据库初始化脚本、环境脚本、环境变量示例 |
| 验收 | 后端与 AI 服务的 health 均返回 200；前端能成功请求后端；数据库可连接且表结构齐全 |
| 依赖 | 无 |

### 8.2 M1 用户系统（Phase 2，3-4 天）

| 项 | 内容 |
|----|------|
| 目标 | 完整的认证与用户管理能力 |
| 任务 | 后端：认证与用户 DTO、校验工具、密码哈希、JWT 工具与过滤器、User/Auth 的 Controller-Service-Repository；前端：登录注册页、鉴权状态、请求拦截器与自动刷新、路由守卫、个人中心 |
| 产出物 | 认证模块前后端 + 用户中心页 |
| 验收 | 注册→登录→带 token 访问用户信息成功；无/过期 token 返回 401；刷新 token 生效；密码非明文入库；用户 A 不能修改用户 B 资料 |
| 依赖 | M0 |

### 8.3 M2 绘本管理（Phase 3，2-3 天）

| 项 | 内容 |
|----|------|
| 目标 | 绘本项目的完整增删改查 |
| 任务 | 后端：Book 三层实现与资源归属校验；前端：绘本列表页、详情页、绘本卡片、绘本状态管理 |
| 产出物 | 绘本模块前后端 |
| 验收 | 绘本 CRUD 全通；列表分页与状态筛选正确；跨用户访问被拒 |
| 依赖 | M1 |

### 8.4 M3 AI 服务基础（Phase 4，3-4 天）

| 项 | 内容 |
|----|------|
| 目标 | AI 服务可独立运行并完成文本解析 |
| 任务 | Pydantic 数据模型、配置与日志、LLM Provider 基类与 Mock 实现、文本分析服务、Prompt 优化服务、Prompt 与风格模板、文本解析接口 |
| 产出物 | AI 服务基础框架与文本解析能力 |
| 验收 | Mock 模式下文本解析返回结构化数据（角色/场景/物品/动作/风格）；接口文档可手工调用；单元测试通过 |
| 依赖 | M0 |

### 8.5 M4 AI 生成闭环（Phase 5 + Phase 8 内存队列版，3-4 天）

| 项 | 内容 |
|----|------|

## 10. 逐步实施引导

> 以下为操作指导，仅描述步骤与完成标志，不含代码。

### 第一步：环境自检

逐项确认：C++ 编译器与 CMake、Drogon 框架、Python 3.10+ 与虚拟环境、Node.js 18+ 与包管理器、Docker 与 Compose、PostgreSQL、Redis、VS Code 及远程开发扩展。

**完成标志**：环境验证清单可全部打勾；示例程序可编译运行；数据库可连接。

### 第二步：仓库骨架

补齐当前缺失的文件与目录：环境变量示例、忽略规则、许可证、数据库脚本目录、文件存储目录、反向代理配置目录、三个子项目目录、测试目录。

同时处理既有不一致：说明文档与初始化脚本引用了尚未创建的环境变量示例；容器编排引用了尚未创建的构建文件、初始化脚本与代理配置。

**完成标志**：目录结构与 Git 规范文档一致；初始化脚本不再因路径缺失而中断。

### 第三步：数据库落地

按第 6 章表清单建立全部表结构，包含主键、外键、索引、唯一约束、级联删除与必要扩展，并补充上传文件表。

**完成标志**：初始化脚本可一次性建库建表；字段与数据库设计文档对齐。

### 第四步：三端骨架联调

分别建立可运行的三端空壳，各自暴露健康检查接口，前端完成一次对后端的成功请求。

**完成标志**：三个端口均可访问且互相可达。

### 第五步至第十一步：按 M1 → M6 顺序开发

每个模块统一遵循以下节奏：

1. 先确定该模块的接口与数据结构
2. 再实现后端 Controller → Service → Repository → Model
3. 再实现前端 API 封装 → 状态管理 → 页面 → 组件
4. 最后走通该模块验收标准，方可进入下一模块

### 第十二步：测试补强

按模块补单元测试，再补接口测试，再补端到端主流程，最后输出测试报告。

### 第十三步：容器化部署

补齐三个镜像构建文件与反向代理配置，跑通一键启动，验证服务间通信与数据持久化。

### 第十四步：报告与演示

按课程报告文档完成九章报告与五分钟演示脚本，并按演示流程彩排。

## 11. 质量保障

### 11.1 开发规范

| 维度 | 措施 |
|------|------|
| 分层 | Controller 无业务逻辑，Repository 无业务规则，Service 承载业务 |
| 前端 | 统一 API 层与状态层，组件职责单一 |
| 命名 | 统一命名规范，接口与数据库字段保持语义一致 |
| 契约 | 所有响应遵循统一响应结构 |

### 11.2 版本管理

- 分支模型：main / develop / feature / release / hotfix
- 提交规范：feat / fix / docs / style / refactor / test / chore / perf，并标注范围
- 关键改动走 Pull Request 评审

### 11.3 测试策略

| 类型 | 工具 | 范围 |
|------|------|------|
| 单元测试 | GoogleTest / pytest / Jest | 核心业务逻辑与工具类 |
| 接口测试 | 自动化脚本 | 全部 REST 接口 |
| 数据库测试 | SQL 与断言 | 持久化、级联删除、索引 |
| 集成测试 | 端到端脚本 | 生成流程等主链路 |
| 端到端测试 | Playwright | 用户主流程 |
| 异常测试 | 用例集 | 认证、授权、上传、AI 超时 |

**目标**：核心功能覆盖率 80%；接口响应时间 < 500ms；首屏 < 3s。

### 11.4 安全基线

1. 密码使用 bcrypt 哈希存储，强度校验
2. JWT 双 Token 机制，支持刷新与撤销
3. 所有资源操作校验归属，实现用户隔离
4. 全部数据库操作使用参数化查询
5. 上传文件校验类型、大小与内容特征，防路径穿越
6. 接口限流与请求体积限制
7. 敏感信息不落日志，密钥通过环境变量注入

### 11.5 可观测性

- 后端使用 spdlog，AI 服务使用标准日志
- 记录 API 响应时间、错误率、并发数、生成成功率
- 任务处理记录耗时与队列状态

### 12.1 技术风险

| 风险 | 影响 | 概率 | 应对措施 |

| WSL 环境问题 | 中 | 低 | 统一以 Docker 兜底 |

### 12.2 时间风险

| 风险 | 影响 | 概率 | 应对措施 |
|------|------|------|---------|
| 功能范围过大 | 高 | 高 | 每个里程碑对照 MVP 边界裁剪需求 |
| 测试时间不足 | 中 | 中 | 边开发边补测试 |
| 报告时间不足 | 中 | 中 | 边开发边积累报告素材与截图 |

### 12.3 进度保护原则
