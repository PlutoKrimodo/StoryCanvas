## 1. 项目是什么（问题定义与系统边界）

面向「不会画画的成年人」（家长 / 幼儿教师 / 绘本创作者）：输入一段故事文字，系统解析出角色/场景/
物品/动作/情绪/风格 → 优化成绘图 Prompt → 调用图像模型出插画 → 绑定到绘本页 → 导出多页 PDF。

端到端主链路（演示看的就是这一条）：

```
故事文字 → 文本解析 → Prompt 优化 → 图像生成（异步任务） → 结果预览
        → 保存到绘本（页绑定 image_id） → 导出多页 PDF
```

**系统边界**（第一件事：说清什么在内、什么在外；按子系统展开的功能边界清单见 §6.1）：

| 边界 | 内容 |
|------|------|
| 系统内 | 用户管理子系统（账号/认证/个人信息/绘本 CRUD）；智能图像生成子系统（解析/Prompt/生成/任务/预览/历史）；轻量多页 PDF 导出 |
| 系统外（依赖） | LLM：DeepSeek；图像：豆包·Seedream（主）/ 通义万相（备）；开发与故障兜底用 Mock Provider |
| 明确不在内 | 在线编辑子系统（画布、元素编辑、图文排版、撤销重做）、角色一致性、内容审核后台 |

边界一划，§6 讲的「约束」（功能边界）就定了一半：**核心能力依赖外部付费服务**，
于是被迫在边界内新增了两道成本闸门（§5 D-2）与「真实厂商 / Mock 双模式」（§5 D-4）；
其余边界依据（课程交付要求、进度、人力与环境、合规）见 §6.3。

## 3. 用户角色与权限（用例视角，对 SRS §9.1 的更正）

| 角色 | 能做什么 | 确认口径 |
|------|---------|---------|
| **游客**（未登录） | 访问 `/` 与 `/generate`、生成插画、预览、下载单图 | 免费额度 **1 张**（`GUEST_GENERATION_QUOTA`），用尽返回 429 并引导登录；首页游客入口只给「登录后保存到绘本」，**但保存动作目前只是产品口径，后端未强制**（见 Q3） |
| **注册用户** | 全部个人功能：绘本增删改查、生成、历史、保存到绘本、导出 PDF | 受全站每日额度约束（§5 D-2） |
| **管理员** | 用户/内容管理 | **本轮不做**，报告里作为「第二阶段 + 内容审核」的未来规划表述 |

- 身份实现：游客是**影子用户**（`users.is_guest`，外键仍 NOT NULL），持 7 天有效期的游客 JWT；
  注册/登录携带 `guest_id` 即**认领**，把游客期间的任务/图片/绘本归属转移到真实账号
  （`backend/services/UserService.cpp` `claimGuestResources`，登录后撤销该用户全部 Token）。
- 游客 Token 走的是同一套 `JwtFilter`（`is_guest` 声明只用于配额判断），因此 `/books`、
  `/generation` 等写接口对游客**在鉴权层面是通的**：「游客不能保存进绘本」目前是**首页入口的
  产品约束**，不是后端约束。需要拍板是否补后端校验，见 §10 Q3。
- **需同步更正**：`docs/01` §9.1「未登录用户只能访问注册/登录页面」已被 T-1 需求取代，见 §5 D-1。
- 资源归属校验口径（已实现且有脚本断言）：**资源存在但不是自己的 → 403；资源不存在 → 404**，
  既守住归属，又不泄露「这个 ID 到底存不存在」。

## 6. 约束 = 功能边界（讲解重点）

**口径说明**：本节按软件工程课程的用法使用「约束」：**约束 = 系统的功能边界**——
系统提供哪些功能（边界内）、明确不提供哪些功能（边界外），以及"做不到"的设计限制。
于是这一节按「边界在哪（6.1）→ 边界怎么裁决（6.2）→ 边界为何在此（6.3/6.4）」三步讲。

### 6.1 功能边界总表（边界内 / 边界外）

| 子系统 | 边界内（做什么） | 边界外（明确不做） | 边界依据 |
|--------|----------------|------------------|---------|
| 用户管理 | 注册/登录/登出、JWT 双 Token、个人信息与改密、绘本 CRUD（分页 + 状态筛选）、资源归属隔离（403/404） | 管理员后台、内容审核、头像上传、第三方登录 | 只保留生成链路所需的最小账号体系；管理后台对单机演示无价值 |
| 智能图像生成 | 文本解析、Prompt 优化（5 套风格）、图像生成（3 尺寸 / 随机种子）、任务五态与取消、结果预览与下载、生成历史与参数复用 | 角色管理与角色一致性、自定义模型、批量生成、图像编辑（涂抹/局部重绘） | 生成闭环是课程主线；角色一致性依赖多图一致技术，工作量不可控 → 第二阶段 |
| 绘本与产出 | 页容器（页号/标题/绑定图）、保存到绘本、多页 PDF 导出（按页序） | 在线编辑子系统全部（画布、元素增删改、移动/缩放/旋转/裁剪、文字排版、撤销重做、图层）、多页手动排版、服务端 PDF 生成 | 编辑子系统工作量最大、与「生成式 AI」主线关系最弱 → 整体放弃；PDF 以「轻量多页」保留 |
| 平台能力 | 游客限额体验（1 张）、全站每日配额（20 张）、真实厂商 / Mock 双模式、本地文件存储 | 100+ 并发承诺、Redis 队列、对象存储、接口限流（未实现，见 Q5） | 单机演示环境用不上；列为第二阶段或如实标注未达标 |

### 6.2 边界判定准则（新需求一律按这四条裁决）

1. **主链路相关性**：是否服务「文字 → 插画 → 绘本 → PDF」这条主链路？
2. **课程主线相关性**：能否体现生成式 AI 与软件工程过程，还是只是通用 CRUD / 前端控件？
3. **外部能力可得性**：外部厂商 API 是否支持？不支持就必须先有替代方案（如 Mock）。
4. **工期与成本可承受性**：能否在剩余工期内完成？是否会增加按次计费的花费？

四条全部通过 → 进本轮；第 1/2 条不通过或第 4 条不可承受 → 边界外（第二阶段或不讨论）。
**D-3 就是一次典型裁决**：主链路相关性通过、工期可承受 → PDF 导出加回，
但切成「轻量多页」（只按页序合成、无排版），**边界的形状并没有被撑大**。

### 6.3 边界依据：为什么画在这里

| 依据 | 事实 | 对边界的影响 |
|------|------|-------------|
| 课程与交付要求 | 九章报告（约 2.5 万字）+ 5–10 分钟现场演示 + 文档/代码可复现 | 边界内只保留可演示、可写进报告的功能 |
| 进度 | 规划总工期 20–29 天；Phase 0–6 与 T-1 已完成，Phase 10–12 未开始 | 边界冻结：新需求先算工期，超期项一律进第二阶段 |
| 人力与环境 | 项目组人力有限、选修课投入时间受限；Windows + WSL 单机开发 | 不做并发承诺；AI 服务并发上限 5、后端用内存队列 |
| 成本 | LLM/图像 API 按次计费、无经费预算、共用一套系统 Key | 边界内新增两道闸门：游客 1 张、全站 20 张/天（按北京时间重置） |
| 部署条件 | 无公网服务器、域名与证书 | 不承诺公网可用性与 TLS 终结；部署降级为 compose 内网 |
| 合规与伦理 | 无内容审核能力；受众是儿童、**创作者是 18+ 成年人** | 内容安全依赖厂商侧审核 + Prompt 约束；不开放「任意图片上传」类功能 |

### 6.4 设计约束（限制「怎么做」，有时也决定「能不能做」）

| 设计约束 | 内容 | 对功能边界的影响 |
|---------|------|-----------------|
| 技术栈 | 后端必须 C++17（课程要求）；AI 服务用 Python；前后端 REST 分离 | 框架只能在 C++ 生态内选（Drogon）；跨语言联调成为主要复杂度 |
| 库与外部服务限制 | 前端 jsPDF 无内嵌中文字体、直出中文乱码；外部模型返回的单张图超过 10MB 会被拒（`MAX_IMAGE_SIZE`） | PDF 改为「html2canvas 把整页（图 + 中文标题）渲染成位图再嵌入」；超限图必须补失败文案（Q8） |
| 数据模型 | 外键 NOT NULL；`book_pages` 降级为页容器 | 游客只能用「影子用户」实现（`users.is_guest`），并配「登录认领」转移归属 |
| 认证与安全 | 所有写接口挂 JWT；密钥只走环境变量；AI 服务 fail-closed | 游客也必须持 Token → 有了「游客 JWT + 配额判断」的设计 |
| 任务执行 | 内存队列 + 工作线程；重试 3 次；超时 LLM 30s / 图像 120s | 不支持大流量并发；演示编排按串行任务设计 |

> 讲这一节推荐的顺序：先给两张清单（6.1），再给判定准则（6.2），最后用 6.3/6.4 解释
> 「边界为什么在这里」——老师想听的不是「时间不够所以砍」，而是**每条边界都有裁决过程**。
> 而 §5 的变更记录，就是这套裁决机制的**证据链**。

### 11.2 三个要主动讲出去的亮点（不等老师问）

1. **需求不是一次成型的**：6 条变更（D-1~D-6）都有「动议 → 评估 → 决策 → 留痕」；
   其中 D-2 是「外部成本」转化为「系统需求」的典型例子。
   本轮共发现**四类不一致**——权限口径滞后（文档仍写「未登录只能看登录页」，实现已是 Guest-first）、
   成本维度缺失（旧需求完全没有这一项，接真实模型后变成硬约束）、
   文档与代码不符（SRS 写了接口限流，代码里只有额度闸门）、
   流程描述过粗（SRS 把「保存到绘本」写成一步到位，实现已解耦为「先出图、后绑页」，
   因此**生成成功 ≠ 已保存**）。
2. **需求是可验证的**：15 条 FR 中 13 条已实现，11 条能指到脚本或单测证据；
   未达标项（接口限流、百并发、未压测）一律如实标注，**不把没做的写进结论**。
3. **功能边界是被主动裁决出来的**：按 §6.2 的四条准则逐条裁决，在线编辑子系统整体判为边界外，
   才换来生成闭环 + PDF 导出的完整交付；这是边界管理与进度保护的结果，不是能力的缺失。
